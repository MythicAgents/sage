# Sage v0.1.0-beta

This beta demonstrates one bounded assisted-mode capability: within the release's exact validated configuration,
Sage can rebuild persistent operation-scoped memory from Mythic, correlate one completed native Apollo `download`
task with its exact current downloaded `.ps1` file record, use one bounded tool-free model call to propose a typed
`credential-material` candidate, deterministically bind its operation/task/callback/file identity, and publish one
canonical top-five finding with exact Mythic source pointers from a background watcher.
The bot-authored `#sage-findings` channel, `/findings`, `/watcher status`, and the generic Mythic event-feed alert
make that result visible without a user initiating an AI-chat turn. The acceptance fixture proves that mechanism.
It does **not** prove that a consultant would have missed the finding or received independent value.

The candidate adds a first-class locked `Sage Watcher` Mythic AI profile. `/watcher apply` establishes one
operation owner generation; creating the channel is inert. Scheduled analysis stays on the direct reasoner while
Watcher conversation uses a separate stateless, tool-free, no-checkpointer explanation graph. Its eight
`SAGE_WATCHER_*` LLM keys reuse Sage Chat's resolution/provider machinery without falling back to ordinary Sage
keys. UI/environment-backed profiles may resume after restart; user-secret-backed profiles wait visibly for the
locked owner to reapply them without copying the secret.

## Authority, data, and resource limits

- Assisted mode is the umbrella over `conversation` and `supervised`; it is not another runtime mode.
  Conversation/background observation cannot task a callback. Supervised execution still requires approval of
  one exact typed action. Auto remains a separate explicit, operation/callback-scoped path.
- Sage operates on the control plane. Target-facing work must execute through a Mythic payload callback, and
  Sage-local attack artifacts are not objective proof.
- Mythic-derived values are client data and can reach the configured model route, checkpoints, Phoenix,
  operation memory, findings, and native Mythic notifications. Operators own LiteLLM/upstream compliance and
  retention. The optional Slack hook sends only a fixed generic notice plus, when explicitly configured for a
  legacy custom-integration webhook, an operator-supplied channel ID. Modern Slack app webhooks remain bound to
  their installed channel.
- The background watcher requires a persistent, operation-bound bot token whose scopes exactly match the frozen
  read/delivery set. It rejects human, wrong-operation, inactive, deleted, wildcard, under-scoped, or over-scoped
  identities; the container-start and AI-channel controller tokens are not durable watcher authority.
- Operation memory is operation-scoped and erasable without modifying authoritative Mythic records. Its five
  configurable defaults are 100,000 model-input tokens, 65,536 inline-text bytes per record, 5 model calls per
  update, 500 records per backfill batch, and 100 queued updates. Exhaustion is visible and resumable.

## Not validated in this beta

Auto mode is GOAD-validated only. Other ranges and production networks; other operating systems or architectures;
other Mythic, Apollo, BloodHound CE, or BloodHound MCP revisions; direct provider routes; other model/provider
combinations; and payload types other than Apollo are not validated. The seeded assisted-capability case is not
consultant-value evidence. See [README Limitations](../../README.md#limitations) and
[Security and Data Handling](../SECURITY_AND_DATA_HANDLING.md) for the complete boundaries.
